## 1. Where things stand

**Done and verified:**
- New extractor `vendor/yt-dlp/yt_dlp/extractor/onlyfans.py` (registered in `_extractors.py`; `lazy_extractors.py` is regenerated by the build).
- It fully reverse-engineers OnlyFans' `api2/v2` request signing at runtime: fetches `app-token`/`x-of-rev` from `app.js`, deobfuscates the per-revision signing rules (rotated RC4 string table + symbolic checksum evaluation) from the site's sign chunk, computes `sign` = `{prefix}:{sha1(static_param\n time \n path \n user_id)}:{checksum:x}:{suffix}`. Byte-exact vs HAR ground truth. Nothing hardcoded from the capture.
- Auth chain works end-to-end: cookies (`auth_id`/`sess`) + `x-bc` + `x-hash` + `sign` are accepted by the API — requests reach the server-side user check.
- Media handling: direct-MP4 creators (`files.full.url` / `videoSources`) produce real formats; DRM-only media fetches the CloudFront-signed HLS manifest and raises the accurate `This video is DRM protected` (VidBee's UI maps this string, `apps/desktop/src/renderer/src/lib/download-error-guidance.ts:116-119`).
- DRM classification for the HAR creator (kenzeygrey) is **proven CDM**, from manifests fetched live with the CloudFront signature:
  - HLS: `#EXT-X-KEY:METHOD=SAMPLE-AES,URI="skd://<REDACTED>",KEYFORMAT="com.apple.streamingkeydelivery"` → FairPlay
  - DASH: `ContentProtection` `urn:uuid:edef8ba9-79d6-4ace-a3c8-27dcd51d21ed` (Widevine) + `urn:uuid:9a04f079-9840-4286-ab92-e65be0885f95` (PlayReady)
- Build/deploy pipeline verified: `pnpm build:ytdlp`, `pnpm verify:ytdlp`, `pnpm run check`, `pnpm build:linux` all pass; AppImage installed at `~/.local/opt/VidBee/current.AppImage` (`vidbee-2.1.0-local-onlyfans-20260916-4f4dff6.AppImage`).

**The open bug (user-reported, reproduced):**
> Every download attempt with valid exported cookies fails with `Wrong user`, **and the attempt itself logs the user's real browser out of OnlyFans.** The user also observed the site logs you out if you switch a desktop session to a mobile viewport — same signature.

## 2. Root cause (evidence-backed hypothesis — treat as near-certain)

**OnlyFans binds a session to the client identity that created it (User-Agent family/platform, sec-ch-ua client hints, and almost certainly the TLS/HTTP2 fingerprint via Cloudflare). Any request carrying the session cookie with a mismatched identity is treated as session theft → the session is revoked server-side → both the script AND the user's browser are logged out.**

Evidence:
| Signal | Brave (session owner, from HAR) | yt-dlp extractor (current) |
|---|---|---|
| User-Agent | `Mozilla/5.0 (X11; Linux x86_64) … Chrome/153.0.0.0 Safari/537.3` | `Mozilla/5.0 (Windows NT 10.0; Win64; x64) … Chrome/148.0.0.0 Safari/537.36` (yt-dlp `std_headers`, `vendor/yt-dlp/yt_dlp/utils/networking.py:18`) |
| Platform | Linux (`sec-ch-ua-platform: "Linux"`) | **Windows** — wrong OS family |
| Client hints | `sec-ch-ua: "Brave";v="153", …` | none sent |
| TLS fingerprint | Chrome/Brave (BoringSSL) | Python OpenSSL — trivially distinguishable (JA3/JA4) |
| `x-bc` | minted by the browser session before capture (no `/key/` request in HAR) | freshly minted by the script each run |

This explains everything observed:
- First Phase-1 test with the HAR cookie jar killed that session → all later API calls returned `{"error":{"message":"Wrong user.","code":101}}` (session already revoked, not a signing bug — signing is byte-exact).
- VidBee's `--cookies-from-browser brave` reads the live cookie store; after one attempt kills the session, the next attempt reads dead cookies → the user's "same error every time" loop.
- The viewport-switch logout is the same binding: `sec-ch-ua-mobile`/UA change → revoke.

## 3. The fix — make the extractor present ONE consistent browser identity

All changes in `vendor/yt-dlp/yt_dlp/extractor/onlyfans.py` unless noted. The vendored yt-dlp already ships `curl_cffi 0.16.0` with Chrome impersonation targets up to `chrome146` (verified: `yt_dlp/networking/_curlcffi.py`, `CurlCFFIRH._SUPPORTED_IMPERSONATE_TARGET_MAP`).

### 3.1 Impersonate Chrome on EVERY OnlyFans request (the critical change)

`_request_webpage` / `_download_webpage_handle` / `_download_json` all accept `impersonate=` and `require_impersonation=` kwargs (`vendor/yt-dlp/yt_dlp/extractor/common.py:866,927`; target type `yt_dlp/networking/impersonate.py:16` `ImpersonateTarget(client, version, os, os_version)`).

Apply to **every** request the extractor makes — post page, `app.js`, sign chunks, `cdn2.onlyfans.com/key/`, `/hash/`, the API call, **and the m3u8/mpd manifest fetch** (`_extract_m3u8_formats(..., impersonate=...)` — verify the kwarg propagates; if it doesn't, fetch the manifest via `_download_webpage` with impersonation and parse with `_parse_m3u8_formats`). Segments/downloads then matter only for non-DRM content.

```python
from ..networking.impersonate import ImpersonateTarget

_OF_IMPERSONATE = ImpersonateTarget(client='chrome', os='linux')
```

Use `require_impersonation=True` so the extractor hard-fails (instead of silently falling back to urllib with a Python fingerprint) if curl_cffi is ever missing from the build.

### 3.2 Send a matching User-Agent + client hints

curl_cffi impersonation sets the TLS fingerprint but yt-dlp's `std_headers` UA (Windows Chrome 148) still goes on the wire unless overridden. Set, on every request:

```
User-Agent: Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/<N>.0.0.0 Safari/537.36
sec-ch-ua: "Chromium";v="<N>", "Not_A Brand";v="8"
sec-ch-ua-mobile: ?0
sec-ch-ua-platform: "Linux"
accept-language: en-US,en;q=0.9
```

`<N>` should match the impersonation target's Chrome version (146 for `chrome146`). Caveat: the user's browser is Chrome **153**; if OnlyFans binds the exact major version, a 146 identity may still trip it. Two options, in order of preference:
1. **VidBee-level (best):** VidBee knows which browser the cookies come from (cookies tab). Have `packages/downloader-core/src/yt-dlp-args.ts` (~line 638, where `--cookies-from-browser` is appended) also pass `--user-agent <that browser's real UA>` (and ideally `--impersonate chrome`). Exact-match UA + Chrome TLS fingerprint is the closest possible identity.
2. Extractor-level fallback: ship the newest available Chrome Linux UA and bump it when the vendored curl_cffi gains newer targets.

Check whether curl_cffi can be upgraded in the vendored tree (`vendor/yt-dlp/uv.lock`) to a version with a `chrome15x` target — that would close the version gap entirely.

### 3.3 `x-bc`: stop minting it from a non-browser client (test empirically)

The browser mints `x-bc` once per session (no `/key/` call in the HAR; the token is stored client-side, likely localStorage) and the observed value is 40-hex (sha1-shaped). The extractor currently fetches `cdn2.onlyfans.com/key/` fresh every run. After 3.1/3.2 this mint looks browser-like and may be fine — **test it**. If session kills persist, investigate reading the browser's stored `x-bc` (Brave profile `Local Storage/leveldb`) or check the site JS for how `/key/` is called (referer/headers) and mirror that exactly. Same question for `/hash/?u=` (x-hash is the raw response body — confirmed from HAR).

### 3.4 Reduce request burst

Cache the site config per revision (already done via `_SITE_CONFIG_CACHE`) and skip re-minting `x-bc`/`x-hash` when a cached config exists. Five rapid requests from a "new device" is exactly what behavioral detection looks for.

## 4. Testing protocol — IMPORTANT, sessions are expendable

Every failed attempt likely revokes the session under test. Do not iterate against the user's daily-driver login carelessly.

1. User logs into OnlyFans in Brave, exports a Netscape cookie jar (e.g. via a cookies.txt extension) to `/tmp/of_cookies.txt`. **Never commit cookie values.**
2. Cheapest probe first — one request, minimal footprint:
   `apps/desktop/resources/yt-dlp_linux --cookies /tmp/of_cookies.txt -s -O '%(id)s' "https://onlyfans.com/<post_id>/<user>"` — or add a temporary debug path hitting `/api2/v2/users/me`.
3. After each attempt, check the browser: still logged in? If logged out → the identity mismatch is still detected; diff your request against the HAR browser request again (§2 table).
4. Only after the browser survives an attempt, run the full `-F` extraction and check the API returns real post JSON (not `Wrong user`).
5. Keep a re-login/re-export loop ready; expect to burn several sessions.

## 5. Scope notes for the follow-up

- **"The manifest should be decoded into mp4" (user expectation):** for the HAR creator this is impossible without a CDM — the manifests are FairPlay (`skd://`) + Widevine/PlayReady (proof in §1). yt-dlp has no CDM and none will be added. **But DRM is per-creator/per-video**: with a surviving session, re-run classification against the user's actual target posts. Non-DRM creators serve `files.full.url` MP4s and the extractor already downloads those (Outcome A). If the user's targets turn out DRM-only, the accurate-DRM failure is the correct end state — set that expectation with the user explicitly.
- **Photos:** the user mentioned "download the image". The extractor currently only handles `media[].type == 'video'`. OnlyFans photos are plain CF-signed JPEGs (`files.full.url`), no DRM — add `photo` support (trivial, big user win). Consider returning them as a playlist of image entries or whatever VidBee's downloader-core accepts for image URLs.
- **Profile URLs** (`onlyfans.com/{username}`): out of scope unless trivial (YAGNI).
- Do not revert VidBee's patches: empty `extractor/unsupported.py`, forced `allow_unplayable_formats` (`YoutubeDL.py:642-644`).
