## The spike and decision D30

`node:sqlite` through `@effect/sql-sqlite-node` was tested on the packaged app's Electron runtime
(43.8.10, Node 24.22.1), Node 22.23.4 and Bun 1.4.4, against a copy of the golden fixture database
and a copy of the owner's database.

| Question | Result |
| --- | --- |
| Opens, reads the same rows and JS types as `better-sqlite3` (20 tables, content checksums) | pass |
| Transactions, savepoints, rollback | pass |
| **A `better-sqlite3` handle and a `node:sqlite` handle on the same file in one process** | **fail: a second writer is admitted while the first holds a write transaction, and an acknowledged insert is gone after commit and reopen.** Two handles of the same driver, or the two drivers in separate processes, block correctly. |
| `Effect.runSync` on SQL-only effects | pass |
| A `SqlClient` over an existing `better-sqlite3` handle, from `effect/sql`'s public constructors | pass |
| Drizzle 1.0 migrator on the existing `__drizzle_migrations` table | pass with a caveat (below) |
| Startup read shapes within 2x of `better-sqlite3` | pass; a 10,000-row insert in one transaction is about 5x slower through the Effect client (27 ms against 4 to 7 ms) |
| Packaging | pass; Node 22 prints an `ExperimentalWarning` on first use, Electron and Bun do not |

**D30 as applied.** `node:sqlite` works as the only driver of a process and cannot share a file
with `better-sqlite3` inside one. Unported code holds `better-sqlite3` handles until the desktop
phases, so:

- Ported code depends only on `effect/sql`'s `SqlClient`.
- During the transition the desktop process keeps one driver, `better-sqlite3`, reached through
  an adapter over the host's existing handle (`BetterSqliteClient`). No second connection.
- `node:sqlite` is the target. When no code in the desktop process holds a raw handle any more
  (phase 9.5 or 10), the composition root swaps the adapter for `@effect/sql-sqlite-node` in one
  change, gated by the golden suite, a launch on a copy of the owner's database, the startup
  timings and a rollback check. If that gate fails, `better-sqlite3` stays behind the adapter.
- `port:check` has a rule, `node-sqlite-before-cutover`, that rejects an import of the node client
  outside `packages/db` until then.

The spike's own recommendation was to keep `better-sqlite3` behind a service for good. The
decision differs only in the end state: once it is the single driver, the spike gives no reason
against `node:sqlite`.

## What was built

- **Row models** for the twelve tables (`History.model.ts`, `TaskQueue.model.ts`,
  `Subscriptions.model.ts`, `Transcripts.model.ts`, `PromptRuns.model.ts`): branded classes in the
  Drizzle property names, a decoder from the snake_case rows raw SQL returns, insert shapes, and
  shared query-shaped schemas (`CountRow`, `ExistsRow`, `IdRow`). A compile-time check ties each
  model's field struct to its table's `$inferSelect` and `$inferInsert` (24 checks).
- **Errors**: `DbMigrationError`, `DbRowDecodeError` (carries the schema issue, never row content).
- **`BetterSqliteClient.layerFromHandle(handle)`**: the transition driver. Borrowed lifetime (never
  opens, closes or reconfigures the handle), synchronous, bounded statement cache with the
  return mode reset in a `finally`, `BEGIN IMMEDIATE` by default with per-operation override,
  savepoints when nested, and savepoints instead of `BEGIN` when the host is already inside its own
  transaction. Also provided under `@effect/sql-sqlite-node`'s tag so Drizzle's Effect driver runs
  on it.
- **`NodeSqliteClient`**: the target driver's layer with VidBee's settings. Used only by this
  package's tests until the cutover.
- **`DbSchema`** (the four schema appliers as effects that read `pragma table_info` themselves)
  and **`Drizzle`** (the `drizzle-orm/effect-sqlite-node` database over the client in context).
- **Legacy entries** (`@vidbee/db/legacy/task-queue`, `/subscriptions`, `/transcripts`,
  `/prompt-runs`): the old tables, DDL constants and callback appliers with unchanged signatures,
  used by desktop (`task-queue-migrate.ts`, `task-queue-host.ts`, `subscriptions-host.ts`,
  `ai-prompt-store.ts`), `subscriptions-core/store.ts` and `transcription/transcript-store.ts`.
  `@vidbee/db/legacy` adds `runtimeForHandle`, `releaseHandle` and `rethrowDriverError` for the
  facades of later phases.
- **PORT-GUIDE** gained a "Database access" section with the seven rules the design sets.

## Drizzle 1.0.0-rc.5

- `drizzle-kit up` converted `apps/desktop/resources/drizzle` to the 1.0 folder layout. The three
  SQL files are byte-identical, so the hashes the owner's database records did not change. The old
  folder is kept as a test fixture.
- The two `drizzle(handle)` calls became `drizzle({ client: handle })`. In 1.0 the old form does
  not fail: it opens a new in-memory database.
- **What changes in an existing database on first launch:** the 1.0 migrator adds two columns,
  `name` and `applied_at`, to its own `__drizzle_migrations` table. Nothing else.
- **Rollback.** The design review found that a *fresh* database created by 1.0 could not be opened
  by the previous build: 1.0 writes second-precision `created_at` values and the 0.45 migrator
  compares against millisecond values, so it would re-run a migration and fail. Desktop's
  `migrate.ts` now writes the original millisecond values after migrating. Tested for existing,
  fresh and partially migrated databases in both directions.

## Design points changed during implementation

The rule set rejected three things the reviewed design asked for; each was decided in the rule
set's favor and the design updated: numeric columns are `S.Finite`, not `S.Number`
(`schemaNumber`); the row models are branded classes tied to the tables through their field
structs (`schemaClassMissingBrand`); `layerFromHandle` takes only the handle
(`missingPipeableSignature`). One consequence is listed in `OWNER-REVIEW.md`: a row holding a
non-finite number or a NULL in a text primary key, both of which SQLite can physically store and
no writer produces, fails to decode instead of being read.

## Found, not fixed (listed in `OWNER-REVIEW.md`)

- `drizzle-kit generate` against the committed snapshots proposes `DROP TABLE download_history`
  and adding `subscriptions.auto_download`, which already exists. The snapshots drifted from the
  schema before the port (the old drizzle-kit proposes the same). Nothing runs `generate`
  automatically; do not apply its output until the snapshots are reconciled.
- Eight places where a Drizzle table object and the real schema disagree (nullability flags on
  primary keys, a missing default on `subscriptions.auto_download`, a missing self-reference on
  `tasks.parent_id`, two partial indexes without their predicates). Pinned as they are.
- A fresh database gets `transcript_segments.words_json` only on the second call of the transcript
  applier, which is how the store calls it. Pinned.

## Not verified

- Windows and macOS.
- The node client inside the running app: by design it is not used there until the cutover.
- The error-identity assertions run on `better-sqlite3` and the adapter only: `node:sqlite` raises
  a different error object (`Error`, `ERR_SQLITE_ERROR`) for the same failure.
- One type assertion remains in `BetterSqlite.driver.ts`, where the client is given the node
  tag's extra members.
