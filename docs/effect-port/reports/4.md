# Phase 4 report: `task-queue`

Phase 4 of the [Effect v4 port plan](../PLAN.md): the task kernel rewritten on Effect, with the
old API kept for its unported consumers. Design: [design/task-queue.md](../design/task-queue.md),
reviewed twice by independent sessions before implementation. The characterization inventory, the
sequencing tables and every gate receipt are in [4-details.md](4-details.md); the real-download
golden cases are described in [4-loopback.md](4-loopback.md).

- [x] Real downloads pinned: 21 golden cases recorded on the pre-port build

## What makes this phase different

The kernel's callers are all unported, and they depend on things the strict rule set cannot
express: synchronous reads and event delivery, promise-level interleaving, a synchronous file
probe, an unref'd timer, synchronous process helpers, zod schemas, `Set`-typed constants. A
`legacy/` directory inside a ported package is still checked by the rule set, so those could only
live there with suppressions, which the standard forbids.

The phase therefore produces **two packages**:

- **`packages/task-queue`** (ported): schemas, 13 services with their layers, the kernel. Effect
  API only. 43 tests on `@effect/vitest`.
- **`packages/task-queue-legacy`** (unported, temporary): the old public API with its exact
  signatures and defaults, running on the new kernel through one `ManagedRuntime` per
  `TaskQueueAPI`, plus the synchronous process helpers and the four zod schemas unported code
  still uses, moved unchanged. 94 consumer files changed their import specifier and nothing else.
  It shrinks as consumers are ported and is deleted in phase 10; until then `port:check` lists it
  as an unported unit.

This departs from the plan's wording (a `legacy` entry inside the ported package) and is in
`OWNER-REVIEW.md`.

## How parity was established

1. **Characterization first.** Before any source changed, 180 `node:test` cases were written
   against the old kernel: every SQLite statement on a real driver, all 64 status pairs of the
   state machine and its guards, every classifier rule, projection formatting, start/stop/restart,
   rollback per operation, listener add and remove during delivery, admission handoff order, and
   twelve operation sequences recorded with microtask markers (store reads, persistence calls,
   events and settlement of the public promise). After the port they run against
   `task-queue-legacy` with only their import specifier changed.
2. **Timing kept on purpose.** The kernel calls a `LegacyTiming.turn` at every place the old code
   awaited; the compatibility package makes it one microtask turn, native consumers get a no-op.
   The compatibility runtime also disables the fiber scheduler's automatic yield and settles its
   promises from the fiber's exit observer, not through `runPromise`. All twelve recorded
   sequences are reproduced exactly; no settlement difference had to be declared.
3. **Real downloads.** The golden harness gained a media server on loopback inside the offline
   namespace, and 21 cases that drive the bundled yt-dlp and ffmpeg through complete downloads
   (video, remux, audio, image, 404, 500, cancel mid-body, pause and resume, duplicate admission,
   manual retry, batch, the automation route, restart on the same profile). They were recorded on
   the build **before** this phase, passed 30 of 30 runs there, and pass unchanged on this
   phase's build.

## Declared changes

Four, each a consequence of the plan's own requirements, each in `OWNER-REVIEW.md`:

1. A persisted task row that does not match its schema is **skipped and logged** (task id and
   schema path, no row content), and the queue starts without it. Before, it was loaded with wrong
   types, or made `start()` throw during a timestamp backfill, after which the desktop fell back
   to an in-memory queue. All 820 task rows of a copy of the owner's database, and the golden
   fixture's, decode.
2. A syntactically invalid JSON column still makes `start()` reject with a `SyntaxError`, but the
   message names the task and column instead of carrying the engine's text.
3. Log lines for caught errors have the logger layer's shape (`{ event, details }`).
4. Under `better-sqlite3`'s safe-integer mode, which no host enables, every integer column is
   converted to a number; before, only two were.

Twenty characterization assertions pinned the old behavior of items 1, 2 and 4. They were
rewritten to the declared behavior with the old expectation kept beside each as a comment; the
table is in the details file. Every other characterization assertion passes unchanged.

## Found, not fixed (in `OWNER-REVIEW.md`)

Behavior the characterization pinned as it is: `maxAttempts` is combined with the category default
by maximum, so a smaller caller value has no effect; `start()` leaves its started flag set after a
failure and a non-empty queue cannot be restarted after `stop()`; `stop()` does not await every
finalization or disarm every watchdog; the orphan event always reports `SIGKILL`;
`importCompleted` bypasses the completion guards; `setMaxPerGroup(key, null)` restores the default
rather than "unlimited"; a panic fallback transition can itself be illegal and replace the
original error; the state machine accepts `NaN` timestamps. From the download cases:
`--trim-filenames 120` truncates the whole output path, not the file name; an audio download
asked for MP3 from a direct WAV URL saves WAV; `durationMs` stays null although the file has a
duration; the raw automation `add` route queues a task with executor defaults instead of the
prepared settings the MCP tool applies.

## Not verified

- Windows and macOS: the native process driver compiles there but was only run on Linux. The app
  still uses the unchanged synchronous process helpers, now in the compatibility package.
- The watchdog path in a real download (its thresholds are 60 and 600 seconds and no setting
  lowers them); it is covered by fake-timer tests.
- Downloads from real sites, which need the network.
